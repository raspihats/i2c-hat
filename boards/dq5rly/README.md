# DQ5rly I2C-HAT

5 relay outputs. **STM32F042K6, LQFP32.**

| | |
|---|---|
| Base I2C address | `0x50` + address-jumper offset (low nibble) |
| Modules | `DigitalOutputs` (`USES_DIGITAL_OUTPUTS`) |
| Channels | 5 relays on TIM3 CH1-4 + TIM1 CH1 |
| BOOT0 pad | PB8 (LQFP32) |
| CubeMX project | `DQ5rly.ioc` (classic `Inc/` + `Src/` layout) |

Version lives in `board.h` (`FW_VERSION_*`) — the single source of truth the
firmware reports over I2C and the one `tools/bump.sh` / `tools/tag.sh` read.
Release history: `git tag -l 'dq5rly-*'`.

```sh
make build BOARD=dq5rly
```

## Board-specific notes

- **It runs its own 1.x version line.** This board joined later than the rest,
  so its numbers sit well below the others' for the *same* core features — the
  1.3.0 release is the same 3.1.0-series bundle the DI boards call 3.1.0.
  Versions are per board by design (RELEASING.md); don't try to align them.
- **Its file names differ from the other F0 boards** — `Startup/` with a
  capital S, and `STM32F042K6TX_FLASH.ld` — because it was generated by a newer
  CubeMX than its siblings. `CMakeLists.txt` names both explicitly, so this is
  harmless; just don't assume the other boards' paths when scripting.
- Its linker script had GCC11-only `(READONLY)` markers stripped so it links
  with GCC10 (harmless on newer toolchains). If CubeMX regenerates the script,
  they come back — strip them again.
- This board is also where the `TIMINGR` divergence was found (it carried the
  higher data-setup margin the whole fleet was later unified onto — see
  PROTOCOL.md); nothing to do, but it explains why its `.ioc` timing value
  looked different from the others historically.
- Relay channels are PWM outputs, not plain GPIOs: the core pulls a relay at
  full drive then holds it at a reduced duty cycle
  (`core/module/digital_outputs.cpp`). TIM1 needs `LL_TIM_EnableAllOutputs()`
  (the MOE bit) in `main.c` or channel 4 stays dead.
